# ANAGEM CMS — Database and permissions

Schema: `backend/src/main/resources/db/migration/` (Flyway; Hibernate runs in `validate` mode so the entities must match the migrations).

| Migration | Content |
|---|---|
| `V1__schema.sql` | All tables, constraints, indexes |
| `V2__seed_access_and_settings.sql` | Permissions, the three roles, default settings, news categories |
| `V3__seed_homepage_and_colloque.sql` | Homepage sections (copy from the Phase 2 prototype) and the documented Kénitra colloque (14–15 Oct 2026) |

V2/V3 are generated by `tools/gen_seed_sql.py` and must not be edited after being applied; change data with a new migration.

## Tables

| Group | Tables | Notes |
|---|---|---|
| Access | `users`, `roles`, `permissions`, `role_permissions`, `revoked_tokens` | Case-insensitive unique email; lockout counters; revoked JWT ids until they expire |
| Media | `media_files`, `media_file_translations` | UUID id; random storage key; checksum; alt text/description per language |
| Categories | `categories`, `category_translations` | **One table for all types** (`NEWS`, `PUBLICATION`, `EVENT`, `RESOURCE`) instead of four near-identical ones |
| News | `news`, `news_translations`, `news_tags` | Slug unique; status + `published_at`; `version` for optimistic locking |
| Publications | `publications`, `publication_translations` | One table for journal issues, books, proceedings, reports (`kind`) — replaces a separate "magazine issue" entity |
| Events | `events`, `event_translations` | `starts_at`/`ends_at` (timestamptz), `all_day`, `event_type`; upcoming/past is computed, not stored |
| Resources | `resources`, `resource_translations` | Documents, maps, research, reports, official, educational; file and/or external link |
| Site | `partners`, `partner_translations`, `homepage_sections` (jsonb), `website_settings` (jsonb) | Homepage text lives in the database, not in code |
| Operations | `audit_logs`, `contact_messages` | Audit keeps the actor's email even if the user is later deleted |

Every translation table is keyed by `(parent_id, locale)`, so any language can be missing without breaking anything, and the dashboard can list the gaps.

**Not built yet** (waiting for institutional decisions, see `docs/requirements`): `members` and `membership_applications` — the statutes define member categories and an approval process, but fees, who approves online applications and what a public directory may show are unconfirmed.

## Roles and permissions

Permissions are rows in the database and each role's set can be changed by a super administrator (`PUT /api/admin/roles/{id}/permissions`); `SUPER_ADMIN` is fixed at "everything". Authorization is enforced on the backend with `@PreAuthorize` on every admin endpoint, independent of the frontend.

| Permission | SUPER_ADMIN | ADMIN | EDITOR |
|---|:-:|:-:|:-:|
| `DASHBOARD_VIEW` | yes | yes | yes |
| `CONTENT_WRITE` (create/edit; move DRAFT ⇄ PENDING_REVIEW) | yes | yes | yes |
| `CONTENT_PUBLISH` (publish, schedule, archive, edit live content) | yes | yes | no |
| `CONTENT_DELETE` | yes | yes | no |
| `MEDIA_UPLOAD` | yes | yes | yes |
| `MEDIA_DELETE` | yes | yes | no |
| `CATEGORY_MANAGE` | yes | yes | no |
| `HOMEPAGE_MANAGE` | yes | yes | no |
| `PARTNER_MANAGE` | yes | yes | no |
| `MESSAGES_VIEW` | yes | yes | no |
| `AUDIT_VIEW` | yes | no | no |
| `USER_MANAGE` | yes | no | no |
| `ROLE_MANAGE` | yes | no | no |
| `SETTINGS_MANAGE` | yes | no | no |

Editorial rules on top of the matrix: editors cannot publish, and cannot edit or delete anything that is already live (`PUBLISHED_CONTENT_LOCKED`); the last super administrator cannot be demoted, disabled or deleted; nobody can disable, delete or change the role of their own account.

## Security notes

- Passwords: BCrypt (cost 12), minimum 12 characters; 5 failed sign-ins lock an account for 15 minutes.
- JWT (HS256, 60 min): secret from `JWT_SECRET` (≥ 32 chars; startup fails otherwise); logout stores the token id in `revoked_tokens`. The user is re-loaded on each request, so disabling an account or changing a role applies immediately.
- No secrets in the repository: production needs `DB_PASSWORD`, `JWT_SECRET`, and (first start only) `BOOTSTRAP_ADMIN_EMAIL`/`BOOTSTRAP_ADMIN_PASSWORD`. If the password is left empty a random one is printed once in the log. The `dev` profile has development-only defaults and loads clearly-marked placeholder content.
- Rate limiting is in memory (one backend instance). Behind several instances move it to the reverse proxy or a shared store. Run the backend behind a trusted proxy only: the client IP comes from `X-Forwarded-For`.
- Not yet done: refresh tokens, per-user token revocation on role change, password-reset by email, malware scanning of uploads.
